# 用户手册

## 你如何开始

先启动自己的完整原生 DSH Web，使用原来的配置、模型和浏览器。控制器的工作目录和 DSH 安装目录可以不同；项目绝对路径决定 DSH 在哪里工作。两端须能访问目标文件和 Host；本工具没有远程文件同步功能。

在 Codex 能读取本仓库后发送：

> 使用 $codex-dsh-collab，连接我的原生 DSH，为【项目绝对路径】完成【目标】，验收标准是【标准】，自主发送、跟随和追修，每阶段汇报，直到完成或我说停止。

首次提供 Host 地址和项目目标。按 [README](../../README.md)运行 setup，它自动安装个人Skill并建立共享连接定位。令牌只通过本地标准输入或token-file提供，不粘贴进聊天。Codex需要本机执行能力、原生Host网络访问及模型任务授权。

setup会将仓库 .agents/skills/codex-dsh-collab 的通用Skill原样安装到个人目录，供其他项目会话发现；路径自动记录在该目录的local-settings.json，无需手动修改Skill。新会话读取个人Skill和配置即可定位工具；已有会话若尚未刷新技能列表，可显式读取个人Skill文件。不同电脑分别setup一次，不复制另一台的cookie或绝对路径。

## 日常表达

- 新任务：“按上述 Skill，在【路径】完成【目标】，不超出【允许范围】。”
- 新聊天续工：“使用 $codex-dsh-collab，继续任务 demo，沿用原状态目录与同一 DSH 会话；先核对项目根、Git 基线和上轮结果再执行。”
- 指定已有会话：“使用已有会话 SESSION_ID，在【项目根】继续【目标】；先核对真实目录、当前活动和权限，已绑定就复用原任务。”
- 查看：“汇报 demo 当前目标、原生会话、进展、下一步和费用可见范围。”
- 停止：“停止任务 demo，不再派发，报告仍未确认停止的原生活动。”

Codex 负责规划和验收，DSH 执行原生任务；正常循环无需你逐轮传话。Codex 会说明本阶段派发了什么、DSH 返回了什么、验收结果和下一步。若停止指令在工具阻塞期间到达，Codex 需要恢复执行机会才能调用停止；不是独立的实时停止服务。

同一任务默认在同一个 DSH session 连续多轮工作，换 Codex 聊天不会自动新建 DSH 会话。Codex 读取个人配置和任务交接后，通用恢复命令为：

```sh
codex-dsh connections
codex-dsh resume --task demo
codex-dsh status --task demo
```

resume 只读历史并恢复观察，不重发旧提示。若要挂靠尚未绑定的指定会话，核对后运行：

```sh
codex-dsh start --connection native --cwd PROJECT_ABSOLUTE_PATH --task demo --session SESSION_ID
```

`attach` 连接 Host；挂靠 session 用 `start --session`，不存在 `attach --session`。同账本已有绑定则复用原 task，不重复挂靠。当前不会自动选出唯一活动任务，也不会在恢复时自动保证真实 cwd 与预期一致；Codex 必须先核对，再继续派发。

也可以直接对Codex说“继续工作区【项目】里名为【会话标题】的对话”。Codex先从原生会话列表核标题和目录，重名时须消除歧义，再找账本已有绑定；这不是CLI已经支持按名称选择。task ID是控制器账本编号，不是DSH原生界面字段；session ID是原生会话身份，界面主要显示可改标题，不能拿标题当唯一ID。查看已绑定的task/cwd/session ID可执行`codex-dsh connections`，用户无需手抄UUID。

## 工作目录与实施分工

项目根、原生 UI 工作区、控制器状态目录是三个不同位置。`--cwd` 用于新会话的工作目录；已有会话的 `--cwd` 参数不会迁移旧会话。`--state-dir` 只选择私有账本。当前 CLI 没有 workspace 命令；原生 API 能注册工作区，本轮仅核对了一次配置和成员读回，未做 UI 视觉验收。Windows 下相同目录的不同斜杠字符串也可能被原生校验拒绝，新建应使用规范 realpath；跨目录或跨项目需新会话或用户明确授权并核对的迁移，不能假装目录已经改变。

Codex 在派发前确认真实 Git 根、branch、HEAD 和已有改动，给 DSH 明确项目/工作区、task/session、允许文件、目标、验收、禁止范围、阶段与费用合同，并指定 `git_owner=Codex`。DSH 承担实施 subagent 的职责，返回变更、实际验证、产物和限制；这是职责分工，不是把 DSH 改成 Codex 原生嵌套 subagent。Codex 负责最终验收及获授权的 Git 操作，DSH 的 COMPLETED 不能代替验收。

长期问题和后续迭代统一看 [已知问题与迭代记录](../validation.md#known-issues)。本地 progress 不另维护一份待办；实际工程写入、测试、追修和 Git 验收闭环仍需单独验证。

## 状态和控制权

跨项目复用setup自动生成的local-settings.json和账本；字段toolRoot、stateDir、connection、url是本机定位元数据，不含秘密。工作区Skill副本也会查个人配置，CLI自动读取同一配置。显式--state-dir可继续旧账本，不能换目录后盲目重建相同任务。首次认证成功后复用连接，Host更换凭证时再次setup；无令牌setup只初始化本地，不保证已鉴权。

完整答复保存在私有状态目录的 reply 文件，命令返回 resultFile。Codex 应读答复并检查真实文件和测试结果，不能只凭“完成”文字接收成果。

COMPLETED 是一个原生轮次完成。SUBMISSION_UNKNOWN 是是否接收不明，不能直接重发。观察超时只结束等待。STOP_PENDING 表示控制器已经阻止新派发，但工具、子任务、共享会话等活动未确认全部静止；仍需查看原生 UI。STOPPED 也不保证整个 Host 的所有后台任务均停止。

原生 UI 可继续看同一会话、审批和接管。附加现有会话使用共享模式；默认新建的任务会话用于减少相互影响。不要同时用不同状态目录控制同一 Host/会话，因为目录间没有全局锁。向任务专属会话人为插入其他任务，也会影响会话级取消的边界。

## 审批

保持 send --wait 或 follow 活跃时，Codex 可查询 approvals，再按你的权限规则提交单次允许或拒绝；也可直接在原生 UI 处理。CLI 的“结果已发送”不是对端肯定采纳的证明，最终以原生事件和实际成果为准。

当前受测安装存在原生审批自动许可的改装。它本来就不发审批事件；此时控制器无法强制它恢复询问，不能把“无待审批”理解为所有操作都经过你确认。源码恢复 fixture 与实际安装的验证要分开看，详见 [验收记录](../validation.md)。

## 费用和上下文

通信层不另设模型输出上限，不转发模型提供方请求，也不截断提示正文。原生上下文窗口和整理策略仍由 DSH/模型决定；这不等于已经实测官方最大输入输出。

双方 token 不保证持平：任务合同、反馈、追修和重新读取可能增加消耗；缓存命中由各自提供方策略决定。工具没有双方合并计费器，也没有提供方内部请求硬上限。按阶段授权与实际提供方账单管理费用；历史有限真实验收不自动授权新任务。

## 故障处理和数据

断线后让Codex在同一状态目录执行resume / follow；它会读原生历史协调，不自动重发。鉴权失效重新setup，保留原账本；高级用法仍可attach。配置错误应修复配置，不得静默回退新目录。CREATE_UNKNOWN或SUBMISSION_UNKNOWN应核对原生会话/文件，避免重复副作用；工具不会猜测任务从未执行。

私有状态含 cookie、提示及答复，默认 .codex-dsh 已加入本仓库忽略规则；在其他项目使用时也应忽略选定目录。目录不提供 OS 沙箱。锁冲突时先确认原进程确已退出，不能靠删锁让两个控制器同时写。保留状态有助于恢复；删除状态会丢失关联。

本工具不在 Codex 配额耗尽、应用退出或主机关闭后继续安排新轮次。原生 DSH 任务可能仍在进行，恢复对话后先查状态。测试范围、源码图和命令含义见 [Codex 手册](codex-guide.md)、[技术说明](../architecture.md)。
