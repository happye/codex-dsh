# 用户手册

## 一句话启动

在目标项目的Codex会话中发送，替换项目路径、目标和验收标准：

> 使用 $codex-dsh-collab，在【项目绝对路径】完成【目标】，以【验收标准】验收；授权本任务必要的原生DeepSeek调用及费用，由你规划验收、DSH实施，按项目规则保留现有改动、建立或复用合同与会话，自主循环追修并阶段汇报，直到验收通过或我叫停，Git提交、推送和部署沿用已有授权。

这句话授权本任务必要的真实DeepSeek调用；如果只想先评估，可改成“先只读评估，不调用真实模型”。逻辑派发轮数不等于提供方请求数，实际费用和调用次数按可见用量记录，不能从“一次send”推定上限。提交、推送和部署仍按项目已有授权，模型调用授权不扩大这些权限。

对用户的使用方式仍是一句话调用Skill；Codex侧新增或强化了工作区核验、合同hash、增量观察、测试回执和停止保护。用户不用手写合同JSON或逐轮传话。

## 新项目的前提和准备

### 一台电脑只做一次

1. 准备Node.js ≥22.19及本工具依赖。工具可独立放在任意目录，不必复制进业务项目；全局npm命令是可选便利方式。
2. 按DSH原有方式配置模型/提供方、工具和权限，启动完整原生Web Host；保留原生UI。Codex须能执行本机命令，访问Host和同一文件系统中的项目目录。本工具不做远程文件同步。
3. 首次运行工具的setup，安装个人全局Skill并生成local-settings.json和共享账本；访问令牌只在本地通过stdin或token-file提供。步骤见[README](../../README.md#准备和运行)。缺少首次认证时才补认证，已有记录不等于Host当前在线。

setup将通用Skill原样安装到个人`$CODEX_HOME/skills/codex-dsh-collab`（未设时为`~/.codex/skills/codex-dsh-collab`），定位与连接写入独立配置。换项目沿用，不重复安装、不复制项目Skill、不重新索取同一令牌。新会话若技能列表尚未刷新，可明确读取该目录的SKILL.md；不同电脑各自setup，不能复制cookie作为通用配置。

### 每个新项目需要什么

用户需要选定项目实际目录，说明目标、允许范围、验收标准，以及本任务的真实模型调用/费用授权；已有项目规则或授权继续有效，无需逐轮确认。

Codex负责完成以下接入：

1. 读取项目指令，核对绝对路径、Git根/分支/HEAD及未提交、未跟踪文件，保留现有成果。工具根、目标项目目录和私有state-dir分别定位。
2. 工程合同的executionRoot必须是有有效HEAD的Git根。空目录应先在获准的初始化范围内建立最小项目文件、git init和初始基线提交；已有项目不重新初始化，不为接入而重置或提交现有未完成改动。单纯连通/只读会话不要求把任意目录改成Git仓库。
3. 确认项目需要的运行环境、依赖和测试命令。Python不是桥接CLI前提，仅在项目或pytest等计划需要时准备；没有已确定测试时testPlan可暂为空，但不代表验收已通过，不创建无断言测试刷绿。
4. 复用本机连接并做实际原生状态核查。需要原生UI工作区时，用workspace列出或注册目标目录，再start --workspace；预先建好工作区不是必要条件，start --cwd也可新建会话。
5. 已有本任务绑定则恢复同一task/session；新目标才创建明确命名的task/session。工程任务绑定允许文件、保护项、要求、测试职责与费用引用后，以contract-sha派发。合同由Codex按项目范围生成，详见[合同手册](contracts.md)。
6. 读取原生答复及实际diff/文件/测试回执，验收或追修；每阶段报告DSH行为、Codex验收、下一步和可见用量，交接时留下task ID以便新聊天继续。

新项目无需重装DSH、改变原生profile、另装调度器或复制整个协作仓库。若目标项目需要隔离工作树，按该项目的允许范围建立；本工具不自动复制或事务合入成果。

## 日常表达

- 新任务：“按上述 Skill，在【路径】完成【目标】，不超出【允许范围】。”
- 新聊天续工：“使用 $codex-dsh-collab，继续任务 demo，沿用原状态目录与同一 DSH 会话；先核对项目根、Git 基线和上轮结果再执行。”
- 指定已有会话：“使用已有会话 SESSION_ID，在【项目根】继续【目标】；先核对真实目录、当前活动和权限，已绑定就复用原任务。”
- 查看：“汇报 demo 当前目标、原生会话、进展、下一步和费用可见范围。”
- 停止：“停止任务 demo，不再派发，报告仍未确认停止的原生活动。”

Codex 负责规划和验收，DSH 执行原生任务；正常循环无需你逐轮传话。Codex 会说明本阶段派发了什么、DSH 返回了什么、验收结果和下一步。若停止指令在工具阻塞期间到达，Codex 需要恢复执行机会才能调用停止；不是独立的实时停止服务。

正常等待优先用有界增量观察，已读且未变的材料复用，阶段汇报聚焦新事实；代码变化后的重验、审批、断线恢复及停止确认保留。具体规则与量化边界见[减少重复读取与等待输出](efficient-collaboration.md)。这改变Codex的调用习惯，不改变DSH原生上下文、工具或完整输出。

同一任务默认在同一个 DSH session 连续多轮工作，换 Codex 聊天不会自动新建 DSH 会话。续接时明确给出原 task ID，并沿用原账本和 session；Codex 读取个人配置和任务交接后，通用恢复命令为：

```sh
codex-dsh connections
codex-dsh resume --task demo --view summary --request latest
```

resume只读历史并恢复观察，不重发旧提示；已有新摘要时不例行再查status。若要挂靠尚未绑定的指定会话，核对后运行：

```sh
codex-dsh start --connection native --cwd PROJECT_ABSOLUTE_PATH --task demo --session SESSION_ID
```

attach连接Host；挂靠session用start --session。同账本已有绑定则复用原task。0.1.2会在附加、恢复和发送前校验原生目录；目录未知或不同会拒绝，不能靠旧READY绕过。

也可以说“继续工作区【项目】里名为【会话标题】的对话”。Codex用tasks --connection NAME --cwd PROJECT_ABSOLUTE_PATH --title EXACT_TITLE查询已有绑定；recover使用同样筛选，唯一匹配才恢复。重名会返回AMBIGUOUS_TASK和候选ID，让主控明确选择；不会猜测、新建或重发。标题可改且可能缺失，task ID才是账本身份；未绑定会话仍需显式start --session。--active只是原生运行/未决请求线索，不代表项目完成与否。

## 工作目录与实施分工

项目根、原生UI工作区、控制器状态目录是不同位置。cwd用于新会话目录，已有会话不会因传参迁移；state-dir只选账本。0.1.2新建自动使用realpath，随后核原生header和本地目录身份。目录须在控制器可访问的同一文件系统；核验不是写入沙箱，合同允许的独立实施树仍需另核Git基线和范围。可用 workspace 列出或注册原生工作区，再以 start --workspace 新建；旧 session 不迁移，指定工作区仅核对现有成员关系。CLI 读回不代替 UI 视觉验收。目录不符时不要编辑账本或旧会话头绕过，应明确核对原任务或新会话。

协作工具仓库和业务目标仓库必须分别管理 Git。DSH 按合同实施并回报；Codex 核对各自仓库的 Git 根、分支、HEAD、差异和允许文件，分别进行获授权的提交与推送。若业务仓库明确指定 main，按其合同操作；工具仓库状态与业务仓库状态分别报告。

Codex 在派发前确认真实 Git 根、branch、HEAD 和已有改动，给 DSH 明确项目/工作区、task/session、允许文件、目标、验收、禁止范围、阶段与费用合同，并指定 `git_owner=Codex`。DSH 承担实施 subagent 的职责，返回变更、实际验证、产物和限制；这是职责分工，不是把 DSH 改成 Codex 原生嵌套 subagent。Codex 负责最终验收及获授权的 Git 操作，DSH 的 COMPLETED 不能代替验收。

真实工程可通过版本化合同记录允许文件、要求与测试职责，再以合同 hash 派发；本地 run、receipt 和 readiness 提供可核验证据及全量门，操作示例见[合同与证据手册](contracts.md)。它们不提供 OS 沙箱或事务合入。

长期问题和后续迭代统一看 [已知问题与迭代记录](../validation.md#known-issues)。本地 progress 不另维护一份待办；实际工程写入、测试、追修和 Git 验收闭环仍需单独验证。

## 状态和控制权

跨项目复用setup自动生成的local-settings.json和账本；字段toolRoot、stateDir、connection、url是本机定位元数据，不含秘密。工作区Skill副本也会查个人配置，CLI自动读取同一配置。显式--state-dir可继续旧账本，不能换目录后盲目重建相同任务。首次认证成功后复用连接，Host更换凭证时再次setup；无令牌setup只初始化本地，不保证已鉴权。

完整答复保存在私有状态目录的 reply 文件，命令返回 resultFile。Codex 应读答复并检查真实文件和测试结果，不能只凭“完成”文字接收成果。

COMPLETED 是一个原生轮次完成。SUBMISSION_UNKNOWN 是是否接收不明，不能直接重发。观察超时只结束等待。STOP_PENDING 表示控制器已经阻止新 send、run 和审批决定，但工具、子任务、共享会话等活动未确认全部静止；仍需查看原生 UI。STOPPED 也不保证整个 Host 的所有后台任务均停止。

0.1.2本地迭代另提供安全停止回执，区分“取消已接收”“原生请求仍运行”和“历史工具活动尚未确认静止”。即使当前请求已中断，最后一种情况仍可返回STOP_PENDING；不要只凭这一状态判断取消失败。

原生 UI 可继续看同一会话、审批和接管。附加现有会话使用共享模式；默认新建的任务会话用于减少相互影响。不要同时用不同状态目录控制同一 Host/会话，因为目录间没有全局锁。向任务专属会话人为插入其他任务，也会影响会话级取消的边界。

0.1.3观察到自建会话被外部客户端共用后，也只停止本工具的继续派发、撤掉自己的排队消息，不取消外部轮次。此时STOP_PENDING是保留其他工作并披露未证静止，不代表强行中止整个会话。原生没有按请求条件取消的接口，不能保证最后检查后新进入的外部请求完全免受竞态影响。

## 审批

保持 send --wait、follow 或 listen 活跃时，Codex 可查询 approvals，再按你的权限规则提交单次允许或拒绝；也可直接在原生 UI 处理。listen 是最多 60 秒的 JSONL 观察窗口，leaseOpen=false 后不可复用旧审批；同一 task 仅开一个 watcher，用另一 CLI 进程提交决定。CLI 的“结果已发送”不是对端肯定采纳的证明，最终以原生事件和实际成果为准。

当前受测安装存在原生审批自动许可的改装。它本来就不发审批事件；此时控制器无法强制它恢复询问，不能把“无待审批”理解为所有操作都经过你确认。源码恢复 fixture 与实际安装的验证要分开看，详见 [验收记录](../validation.md)。

## 费用和上下文

通信层不另设模型输出上限，不转发模型提供方请求，也不截断提示正文。原生上下文窗口和整理策略仍由 DSH/模型决定；这不等于已经实测官方最大输入输出。

usage 可导出当前任务原生请求的脱敏计数及缺失说明，不含消息正文。summary/generation 可避免重复展开旧答复，但仍须读完整产物验收。双方 token 不保证持平：任务合同、反馈、追修和重新读取可能增加消耗；缓存命中由各自提供方策略决定。工具没有双方合并计费器，也没有提供方内部请求硬上限。按阶段授权与实际提供方账单管理费用；历史有限真实验收不自动授权新任务。

## 故障处理和数据

断线后让Codex在同一状态目录执行resume / follow；它会读原生历史协调，不自动重发。鉴权失效重新setup，保留原账本；高级用法仍可attach。配置错误应修复配置，不得静默回退新目录。CREATE_UNKNOWN或SUBMISSION_UNKNOWN应核对原生会话/文件，避免重复副作用；工具不会猜测任务从未执行。

错误可附带diagnostic：固定类别、发生阶段、关联RPC ID和knownRejected。只有已确认在派发前拒绝才可认定该操作未执行；内部、未知和取消错误即便有原生错误响应，也保留不明状态。工具不打印原生message/details或凭证。Node原生退出断言仍是独立待复现问题，安全诊断不代表它已修复。

私有状态含 cookie、提示及答复，默认 .codex-dsh 已加入本仓库忽略规则；在其他项目使用时也应忽略选定目录。目录不提供 OS 沙箱。锁冲突时先确认原进程确已退出，不能靠删锁让两个控制器同时写。保留状态有助于恢复；删除状态会丢失关联。

本工具不在 Codex 配额耗尽、应用退出或主机关闭后继续安排新轮次。原生 DSH 任务可能仍在进行，恢复对话后先查状态。测试范围、源码图和命令含义见 [Codex 手册](codex-guide.md)、[技术说明](../architecture.md)。

额度耗尽后的自动接管、常驻调度与循环提醒已排除出本项目路线。恢复Codex后，先恢复原任务和核对DSH已发生的工作，再继续原合同；不重发不明请求。
